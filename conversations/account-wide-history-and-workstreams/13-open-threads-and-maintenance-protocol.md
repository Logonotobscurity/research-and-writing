# 13 — Open Threads, Evidence Register, and Maintenance Protocol

## 1. Purpose

This document keeps the archive useful without allowing summaries to harden into unsupported facts. It identifies important open questions and defines how new evidence should be added.

## 2. Cross-account open threads

### Research and systems-building practice
- Collect project episodes showing how investigation changed the initial problem definition.
- Identify how the user decides there is enough evidence to begin architecture.
- Compare discovery, delivery, integration, and validation across contexts.
- Preserve counterexamples as well as confirming examples.

### LOG_ON and commercial validation
- Verify current service catalogue and website messaging.
- Identify which growth systems have paying customers and measurable outcomes.
- Validate pricing, delivery cost, acquisition channels, and retention.
- Separate the proposed dental-clinic proof and tier ideas from achieved results.
- Decide which offerings should be services, products, or internal platform capabilities.

### Agent runtime and assurance
- Verify implementation status of the execution kernel and runtime specifications.
- Establish an authoritative tool registry and permission model.
- Define risk tiers and approval requirements.
- Test prompt/context injection, credential boundaries, tenant separation, retries, partial execution, rollback, and audit completeness.
- Define measurable release gates.

### PAL and African-language research
- Verify repository and experiment status.
- Inventory actual datasets, licences, annotations, and language coverage.
- Establish reproducible transcription and semantic baselines.
- Separate transcription performance from meaning and action correctness.
- Test action gates under code-switching and noisy audio.

### Memory and consent products
- Re-audit ContextPocket, Re:Mind Me, and MorrowVoice.
- Verify OAuth and background-sync state.
- Test actual MCP approval UX across clients.
- Confirm tenant isolation, access filtering, retention, export, correction, deletion, and audit.
- Ensure inference never silently becomes verified identity or consent.

### Product portfolio
- Mark projects active, paused, archived, or conceptual.
- Trace public claims to repositories, releases, demos, or outcomes.
- Verify Clip Creator Studio end-to-end operation.
- Recheck GroundedGuide differentiation without disclosing private reference material.
- Verify GigPilot metrics.
- Avoid presenting components and blueprints as shipped products.

### Technical research and learning
- Validate course names, providers, durations, cost, and availability.
- Verify notebook-generated claims against primary sources.
- Benchmark retrieval on representative data and realistic permissions.
- Establish evaluation criteria before selecting databases or frameworks.
- Distinguish demonstrated skill from inferred proficiency.

### Opportunity and career
- Recheck deadlines and eligibility before applications.
- Update CV with verifiable outcomes.
- Confirm portfolio links, repository state, and contribution metrics.
- Build a repeatable opportunity-to-application workflow.

### Writing framework
- Preserve the distinction between truthful tension and coercive pressure.
- Reassess identity-labeling and reactance claims against primary research.
- Test the writing framework across technical, interpersonal, commercial, and editorial contexts.
- Retain hard-stop rules for Truth and Agency.

## 4. Project evidence template

For each workstream, maintain:
- Name and classification.
- Problem, user, and intended outcome.
- Current maturity: concept, design, prototype, MVP, production, paused, or archived.
- Source of truth: repository, branch, specification, issue, or paper.
- Last verified date and method.
- Evidence: tests, traces, user feedback, usage, releases, or study results.
- Known gaps: technical, product, security, adoption, or operational.
- Decision: proceed, test, defer, split, merge, or archive.
- Next action, owner, and validation criterion.

## 5. Update protocol

1. Identify the distinct topic or workstream.
2. Check whether an existing document covers it.
3. Add a dated section or create a new numbered document if genuinely distinct.
4. Preserve exact user wording where available and useful.
5. Label reconstructed summaries as synthesis.
6. Separate user intent from assistant interpretation.
7. Record decisions, reversals, and reasons.
8. Link the note from the local README and phase map.
9. Update the repository root README for a new conversation folder.
10. Verify links and writes.

## 6. Naming and formatting conventions

Use lowercase kebab-case filenames, numeric prefixes for ordered documents, descriptive headings, tables for concise inventories, and diagrams only where they represent a real workflow. Give each folder a README. Do not rename an older folder simply to impose a new taxonomy.

## 7. Final principle

This is a working knowledge record, not a fixed biography or marketing profile. It should make future investigation, product design, engineering, writing, and strategy more coherent while keeping uncertainty visible. Accuracy is more important than appearing complete.
